When we started cataloguing feeds for AI practitioners, the first instinct was to use tags. Every feed gets a few keywords: `machine-learning`, `nlp`, `python`, `research`. Simple to implement, easy to understand.

We abandoned that approach about two weeks in.

## The problem with flat tags

Tags work well when the label space is small and the items are roughly equivalent in scope. They fall apart when you're trying to model a domain with genuine hierarchical structure.

Consider the tag `transformers`. Does it mean:

- The neural architecture family introduced in "Attention Is All You Need"?
- The broader category of attention-based sequence models?
- Large language models specifically?
- A specific library (Hugging Face Transformers)?

A flat tag can't answer this question. An ontology can.

When a user asks for feeds about "large language models," they probably also want feeds about fine-tuning, RLHF, model evaluation, and inference optimisation — not because those share a tag, but because they're semantically related in a structured way.

## The DAG model

Our taxonomy represents topics as nodes in a directed acyclic graph (DAG). Each topic can have:

**Parent relationships** — "Transformer Models" is a parent of "Large Language Models," which is a parent of "Instruction Tuning." This gives us hierarchical rollup: a feed tagged with "Instruction Tuning" is also, transitively, about LLMs and transformers.

**Related relationships** — bidirectional associations between topics that share conceptual overlap without one being a subtype of the other. "Retrieval-Augmented Generation" and "Vector Databases" are related, not parent/child.

**Supersedes relationships** — for cases where a newer framing has largely replaced an older one. "Foundation Models" partially supersedes the older "Pre-trained Models" terminology.

## Facets carry structured metadata

Each topic node carries facets that enable richer filtering than a keyword alone:

```yaml
- id: large-language-models
  label: Large Language Models
  description: Autoregressive transformer models trained at scale on text corpora
  facets:
    type: technology
    domain: artificial-intelligence
    technical_depth: advanced
    maturity: production
  parents: [transformer-models]
  related: [instruction-tuning, rlhf, model-evaluation, inference-optimization]
```

The `type` facet distinguishes technologies, methodologies, communities, and domains. The `technical_depth` facet enables filtering for beginner versus advanced content. The `maturity` facet distinguishes cutting-edge research from production-ready practice.

## Why this matters for feed discovery

The taxonomy isn't decorative — it's operational. When the catalog assigns a topic to a feed, the entire ancestor chain is queryable. A feed tagged with `rlhf` is also retrievable via queries for `llm-alignment`, `machine-learning`, and `artificial-intelligence`.

This means you can build navigation and filtering that respects the actual structure of the knowledge space rather than flattening it into a keyword soup.

The [feed explorer](/explorer) uses the topic graph directly for its visual layout — nodes in the graph visualisation correspond to actual taxonomy entries, and feeds cluster around their most specific applicable topics.

## The graph is a first-class data dependency

The full taxonomy lives in `data/topics.yaml` and is validated against a JSON Schema on every commit. It's not documentation — it's data that the application reads at runtime.

We treat it like a dependency: changes go through review, relationships are bidirectional-checked for consistency, and the schema enforces required fields.

If you're building a system that needs to reason about AI and technology domains, the taxonomy is available via the API at `/api/topics` and as part of the feed catalog export.
