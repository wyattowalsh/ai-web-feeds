# Visualization API Reference

This page documents the visualization backend that exists in the repository
today. It intentionally reflects the live Python routers and models rather than
older planning-only contracts.

## Base paths

- Visualization APIs: `/api/v1`
- Export APIs: `/api/v1/export`

## Authentication

All visualization and export endpoints rely on:

- `Authorization: Bearer <jwt>`
- or `X-API-Key: awf_...`

The authenticated token or key resolves the active `device_id`.

## Stable enums

### Chart types

`line`, `bar`, `scatter`, `pie`, `area`, `heatmap`

### Data sources

`feeds`, `topics`, `articles`, `entities`, `sentiment`, `quality`

### Widget types

Canonical values:

- `chart`
- `metric_card`
- `feed_list`
- `topic_cloud`

Accepted compatibility aliases include `metric`, `metricCard`, `list`, `table`,
and `cloud`.

### Export status

Canonical value:

- `in_progress`

Accepted compatibility aliases:

- `processing`
- `inProgress`

## Visualization endpoints

### `GET /api/v1/visualizations`

List saved visualizations for the current device.

Query params:

- `limit` (default `50`, max `100`)
- `offset` (default `0`)

### `POST /api/v1/visualizations`

Create a visualization.

Request fields:

- `name`
- `chart_type`
- `data_source`
- `filters`
- `customization`

The backend normalizes legacy filter/customization aliases before storage.

### `GET /api/v1/visualizations/{visualization_id}`

Fetch a saved visualization and update its `last_viewed` timestamp.

### `PUT /api/v1/visualizations/{visualization_id}`

Update a visualization. Validation failures return a normalized `400` detail
payload.

### `DELETE /api/v1/visualizations/{visualization_id}`

Delete a visualization for the current device.

### `POST /api/v1/visualizations/{visualization_id}/data`

Fetch records for a saved visualization. The backend uses:

- visualization filters normalized to snake_case
- request `date_range` overrides when provided
- stored visualization `date_range` otherwise

## Dashboard endpoints

### `GET /api/v1/dashboards`

List dashboards for the current device.

### `POST /api/v1/dashboards`

Create a dashboard with canonical `layout` storage. `layout_config` remains a
compatibility alias on the model surface.

### `GET /api/v1/dashboards/{dashboard_id}`

Fetch a dashboard. `include_widgets=true` by default.

### `PUT /api/v1/dashboards/{dashboard_id}`

Update a dashboard with optimistic-locking version checks.

### `DELETE /api/v1/dashboards/{dashboard_id}`

Delete a dashboard and its widgets.

### `POST /api/v1/dashboards/{dashboard_id}/widgets`

Add a widget using canonical widget types and `position: {x, y, w, h}`.

## Export endpoints

### `GET /api/v1/export/tables`

List exportable analytics tables and columns.

### `GET /api/v1/export/data/{table}`

Direct export for a single table.

Query params:

- `format` = `json | csv | parquet`
- `limit` (default `1000`, max `10000`)
- `cursor` (reserved passthrough)
- `sort_by` (reserved passthrough)
- `sort_order` = `asc | desc`

### `GET /api/v1/export/stream/{table}`

Stream large exports in batches.

Query params:

- `format` = `json | csv`
- `batch_size` (default `1000`, max `5000`)

### `POST /api/v1/export/bulk`

Generate bulk export URLs for up to `10` tables.

Query params:

- `format` = `json | csv | parquet`

Request body:

- JSON array of table names

## Validation error model

Validation failures return HTTP `400` with this normalized structure:

```json
{
  "detail": {
    "code": "invalid_limit",
    "message": "Limit must be positive",
    "field": "limit"
  }
}
```

Optional `details` may include allowed values or max limits.

## Compatibility note

Older planning artifacts still mention async export jobs and additional export
endpoints. Those are not part of the runtime contract until the Python router
implements them.
