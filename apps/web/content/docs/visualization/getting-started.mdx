# Visualization & Analytics

The visualization backend is currently exposed through the versioned `/api/v1`
surface and a set of device-scoped SQLModel entities in
`ai_web_feeds.visualization`.

## Current runtime surface

- **Visualizations**: CRUD for line, bar, scatter, pie, area, and heatmap charts
- **Dashboards**: CRUD plus widget placement and optimistic-locking updates
- **Forecast models**: canonical `forecast_horizon_days` with legacy `horizon_days`
  compatibility
- **Table exports**: direct, streaming, and bulk table export helpers for JSON,
  CSV, and Parquet
- **Cache layer**: Redis-first with in-memory LRU fallback and 300-second query TTL

<Callout type="info">Chart image export (`png`, `svg`, `html`) is currently an in-browser web helper. The backend export router is for structured table data (`json`, `csv`, `parquet`).</Callout>

## Authentication

Visualization and export endpoints accept either:

- `Authorization: Bearer <jwt>`
- `X-API-Key: awf_...`

The backend resolves the active `device_id` from the authenticated token or API
key. It does **not** accept a raw `device_id` query parameter on the runtime
export endpoints.

## Cache behavior

The live query consumers in `DataService` currently use the versioned cache key
format:

```text
v1:query:{query_type}:{sha256(normalized_payload)}
```

Key details:

- Filters and date ranges are normalized before hashing
- Canonical and legacy alias payloads map to the same cache entry
- Query TTL is **300 seconds** for visualization queries, including topic graph data
- Invalidation is query-type based (`topic_metrics`, `feed_health`, `topic_graph`)

## Validation behavior

Validation failures now normalize into a stable detail shape for API consumers:

```json
{
  "detail": {
    "code": "invalid_table_name",
    "message": "Table 'foo' not allowed.",
    "field": "table_name",
    "details": {
      "allowed_values": ["article_metadata", "feed_health", "topic_metrics", "validation_logs"]
    }
  }
}
```

In-process Python callers still get the same `str(error)` message for backwards
compatibility.

## Export endpoints available today

The current backend export router lives under `/api/v1/export`:

- `GET /api/v1/export/tables`
- `GET /api/v1/export/data/{table}`
- `GET /api/v1/export/stream/{table}`
- `POST /api/v1/export/bulk`

The runtime contract does **not** currently expose async export jobs,
`/export/formats`, or `/export/jobs/*` endpoints.

## Compatibility highlights

The canonical wire format is snake_case, but the backend still accepts and, for
key models, emits selected legacy aliases such as:

- `processing` → `in_progress`
- `layout_config` ↔ `layout`
- `position_x` / `position_y` / `width` / `height` ↔ `position`
- `horizon_days` ↔ `forecast_horizon_days`
- `metrics` ↔ `accuracy_metrics`
- `file_path` ↔ `file_url`
- `error` ↔ `error_message`
- `status_code` ↔ `response_status`

See the dedicated compatibility policy for the complete list and deprecation
rules.
