# Security Policy

This page documents how to report vulnerabilities and how the live repository
separates anonymous public behavior from admin-only controls.

## Reporting a vulnerability

<Callout type="warn" title="Private disclosure only">
  Do not open public issues for suspected security vulnerabilities.
</Callout>

<Steps>

### Preferred: GitHub Security Advisories

1. Open <a href="https://github.com/wyattowalsh/ai-web-feeds/security/advisories">the repository security advisory page</a>.
2. Choose **Report a vulnerability**.
3. Include reproduction steps, impact, and affected files or routes.

### Alternate: secure email

Send a report to `wyattowalsh@gmail.com` with **SECURITY** in the subject line.

</Steps>

Please include:

- affected paths or workflow files
- the commit, branch, or deployment context
- exact reproduction steps
- expected impact and any proof-of-concept details

## Trust boundaries

### Anonymous public surface

Public catalog and reader-facing flows do **not** require end-user accounts.
The repository intentionally keeps public behavior anonymous and device-scoped.

That means:

- catalog APIs such as `/api/feeds` and `/api/topics` are public read surfaces
- browser-local reader state stays on-device
- user-scoped web APIs rely on a stable anonymous UUID plus a server-issued
  binding cookie rather than a user login system

<Callout type="info" title="Anonymous does not mean unscoped">
  Public flows are anonymous, but user-specific state still needs a stable, trusted identifier. The server binding cookie exists to prevent one client from mutating another client’s follows, preferences, or saved state.
</Callout>

### Admin-only surface

The only authenticated surface is `/admin`.

- admin access requires `AIWF_ADMIN_PASSWORD`
- sessions are signed with `AIWF_ADMIN_SESSION_SECRET`
- admin sessions are stored in an HttpOnly cookie
- login attempts are throttled before a session is issued
- middleware protects `/admin` page routes, while admin API routes validate
  auth in the route handlers themselves

## Workflow and release safety

Repository automation follows a narrow-mutation model:

- `.github/workflows/*.yml` are the active workflows
- `.github/workflows/*.md` are experimental GitHub Agentic Workflow sources
- agentic pilots must stay additive and read-only by default
- release publishing uses GitHub OIDC trusted publishing rather than long-lived
  PyPI credentials
- feed-submission automation validates first and only opens a PR after explicit
  maintainer approval

## Automated security checks

The live automation stack includes:

- **CodeQL** for code scanning
- **Dependency Review** for dependency changes in pull requests
- **Dependabot / dependency refresh workflows** for update hygiene
- **GitHub secret scanning and workflow permission controls**

## Contributor checklist

```bash
uv run python data/validate_data_assets.py
uv run pytest
pnpm --dir apps/web build
pnpm --dir apps/web lint:links
```

Use these checks before proposing changes to auth, workflow mutation paths,
public APIs, or data-validation logic.

## Safe harbor expectations

Researchers and contributors should:

- act in good faith
- avoid privacy violations and destructive testing
- use only accounts, devices, or repositories they control or are authorized to test
- stop after demonstrating impact and report the issue promptly
