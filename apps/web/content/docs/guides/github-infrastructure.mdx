# GitHub Infrastructure

The `.github/` directory owns issue intake, workflow automation, prompts, and
repository-specific agents. This page summarizes the live structures contributors
should know before editing workflow or intake files.

## Issue forms

Current issue templates include:

- `add-feed.yml`
- `feed-update.yml`
- `bug-report.yml`
- `feature-request.yml`
- `documentation.yml`
- `cli-issue.yml`
- `workflow-issue.yml`

These forms are configured through `.github/ISSUE_TEMPLATE/config.yml`, which
controls the issue-creation experience and directs users toward supported paths.

## Pull request template

`.github/pull_request_template.md` is the shared PR checklist for code quality,
testing, docs, and data changes.

## Workflow structure

| Workflow family                  | Representative files                                                                                   |
| -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| quality and CI                   | `quality-enforcement.yml`, `coverage.yml`, `python-quality.yml`, `ci.yml`                              |
| feed intake and catalog mutation | `validate-feed-submission.yml`, `add-approved-feed.yml`, `validate-all-feeds.yml`, `process-feeds.yml` |
| release and maintenance          | `release.yml`, `release-drafter.yml`, `dependency-updates.yml`, `stale.yml`, `sync-labels.yml`         |
| security and review              | `dependency-review.yml`, `codeql-analysis.yml`, `pr-validation.yml`, `label-manager.yml`               |

## Validation and approval model

1. a feed issue is normalized with `.github/scripts/feed_submission_to_source.py`
2. duplicate URLs are rejected before mutation
3. repository data assets are validated
4. the issue receives `validated` or `validation-failed`
5. a maintainer may then apply `approved`
6. approval opens a PR instead of editing `main` directly

The deterministic workflows now also emit machine-readable summaries for the
distillation layer and extract them into stable additive workspace paths for
gh-aw consumption:

- `reports/github/catalog/feed-processing-summary.json`
- `reports/github/feed-submissions/issue-<number>/normalized-source.json`
- `reports/github/feed-submissions/issue-<number>/validation-summary.md`
- `reports/github/feed-submissions/issue-<number>/snapshot-manifest.json`
- `reports/github/feed-submissions/issue-<number>/feed-submission-validation-summary.json`

These `reports/github/...` paths are extracted workflow evidence, not checked-in
catalog data.

<Callout type="info" title="Why this is safe">
  The workflow chain is intentionally additive. Validation comments and labels are cheap to rerun; repository mutation only happens through a reviewable PR.
</Callout>

## Agentic workflow pilots

The repository also contains `.github/workflows/*.md` gh-aw source files. These
are **not** active workflows until they are explicitly compiled, reviewed, and
adopted. Treat them as an additive distillation layer on top of the canonical
YAML workflows, and keep pilots read-only or report-only unless there is a
reviewed adoption plan.

## Local dry run commands

```bash
uv run python .github/scripts/feed_submission_to_source.py \
  --event-path reports/feed-submission-event.json \
  --output-source reports/parsed_feed.json \
  --output-summary reports/parsed_feed_summary.md
uv run python data/validate_data_assets.py
```
