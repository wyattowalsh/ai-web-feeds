# Search & Discovery

The Search & Discovery experience lives inside the unified `/feeds` workspace
and now answers two different questions from one route:

- **What should I read now?** Browse and search the generated article corpus.
- **Which sources should shape that queue?** Switch to catalog mode and refine
  the source slice.

## Workspace model

`/feeds` is now the default reader-first route.

- `/feeds` opens the article workspace
- `/feeds?mode=catalog` opens the explicit source picker
- legacy `mode=articles` and `mode=reader` URLs still normalize into the same
  reader-first workspace state

The workspace keeps its query, filters, pinned feeds, sort order, and local
reader view in the URL so deep links stay shareable and restorable.

## Article browse and search

Article browse and article search are backed by `data/articles.generated.json`,
which is exported from `feed_entries` in the runtime database.

That means the reader workspace can:

- search titles, summaries, feed titles, authors, categories, and topics across
  the exported corpus
- filter by `feed`, `topics`, `source_type`, and `verified`
- page through results with cursor-based pagination
- sort by `latest`, `oldest`, or `source`

The article list is served by `GET /api/articles`, while ranked article search
uses `GET /api/search?scope=articles`.

## Catalog search

Catalog search remains backed by the checked-in feed catalog.

Use catalog mode when you want to:

- filter feeds by source type, topic, or verification state
- pin one or more feed IDs into the article workspace
- move from source discovery into the reader without leaving `/feeds`

This keeps source discovery available even if the runtime corpus has not been
generated yet.

## Autocomplete

Autocomplete now returns a shared suggestion set sourced from the catalog plus
the article corpus:

- matching feeds
- matching articles
- matching topics

Because the same server-side adapter builds those suggestions, autocomplete and
article search no longer drift across different data models.

## Freshness overlay

The canonical reader/search dataset is the generated corpus. Live feed fetches
still exist, but only as an explicit freshness overlay.

- `Refresh latest` calls `/api/feeds/posts/aggregate`
- new live items are deduped against the current corpus-backed list
- genuinely new items are prepended with a freshness badge
- failed refreshes do not replace or erase the base corpus results

## Local reading state

Unread, saved, starred, and archived state stay in browser-local storage.

Those client-only states are layered on top of server-returned article results,
which is why you can filter the visible list to `unread`, `saved`, `starred`,
or `archived` without writing that state into the generated corpus artifact.

## Analytics logging

If a Python backend is configured, the web app can still log executed searches
through `POST /api/search` using the anonymous identity bootstrap.

If no backend is configured:

- browse/search/autocomplete continue to work
- only the analytics write is skipped

## Configuration

```bash
# Optional backend for search analytics logging
BACKEND_URL=http://localhost:8000
```

## Usage

### Web Interface

Navigate to `/feeds`:

1. Type a query in the workspace search bar
2. Keep or adjust the shared source-type, topic, verified, and pinned-feed filters
3. Press Enter to refresh the article list, or use autocomplete suggestions
4. Switch to `mode=catalog` when you need to change the source slice
5. Use `Refresh latest` when you want a non-destructive live overlay on top of the corpus

**Keyboard Shortcuts**:

- `Cmd/Ctrl+K`: Focus search bar
- `Arrow keys`: Navigate autocomplete suggestions
- `Enter`: Execute search

### CLI

```bash
# Catalog search
uv run ai-web-feeds search "transformer attention" --limit 20

# Filter by source type and topic
uv run ai-web-feeds search "pytorch" --source-type blog --topic deeplearning

# Autocomplete against the catalog
uv run ai-web-feeds search autocomplete openai --limit 5
```

### API

```typescript
// Corpus-backed article browse
const browse = await fetch("/api/articles?q=agents&sort=latest&limit=24");

// Source search
const response = await fetch("/api/search?q=transformer&scope=sources&limit=20");
const results = await response.json();

// Article search
const articleResults = await fetch("/api/search?q=neural%20networks&scope=articles&limit=20");

// Autocomplete
const suggestions = await fetch("/api/search/autocomplete?prefix=mach");
```

## Performance

- **Autocomplete**: Shared catalog/corpus suggestions with cacheable GET responses
- **Source Search**: Reads checked-in data without depending on a backend runtime
- **Article Browse/Search**: Reads the generated corpus artifact instead of running live feed scans on demand

## Zero Results Handling

When no article results are found, the UI steers the user toward:

- returning to catalog mode for broader source discovery
- fewer filters
- a wider topic or source-type scope
- rebuilding the generated corpus if the workspace reports that the artifact is unavailable

## Success Criteria

- ✅ Reader-first `/feeds` works without a required Python HTTP backend
- ✅ Article browse and article search run across the generated corpus
- ✅ Source results can jump directly into the article workspace within `/feeds`
- ✅ Autocomplete suggestions are built from the same catalog/corpus model used by the reader
