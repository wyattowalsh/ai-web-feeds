The recommendations page is optional. It depends on the Python backend, so it is only fully available when `BACKEND_URL` points to a running `ai_web_feeds.web_api` service.

## What It Does

The recommendations page at `/recommendations` is wired to real backend routes, but it remains a secondary surface behind the reader and source catalog. When the ai-web-feeds backend is configured, the page loads personalized suggestions and records recommendation interactions. When it is not configured, the page shows one explicit unavailable panel and routes people back to the catalog instead of failing noisily.

- load ranked source suggestions
- explain why a source was suggested
- let you refine recommendations with topic chips
- record actions such as view, click, subscribe, and dismiss

## Backend Requirement

Recommendations are not part of the standalone web-only profile.

If `BACKEND_URL` is missing or the backend is unavailable:

- the page shows a clear unavailable state
- the proxy routes return `503 FEATURE_UNAVAILABLE`
- Feeds and the catalog continue to work normally

- ranked feed recommendations
- recommendation reasons such as `similar_topics`, `popular`, `discover`, and `similar_content`
- topic chips for steering the current slice
- feed actions for opening a result in `/?mode=catalog`, subscribing, or dismissing it

### Personalization Input

The web client creates a stable local `user_id` in `localStorage` and sends it with every recommendation request. Topic chips refine the current request without changing the page URL, so personalization can persist locally without requiring user accounts.

### Interaction Tracking

The UI records these interaction types:

- `view`
- `click`
- `subscribe`
- `dismiss`

The backend stores that feedback, updates the user profile, and uses it to avoid repeating previously followed or already-interacted feeds in later recommendations.

### Unavailable State

If `BACKEND_URL` is missing or the backend is unavailable, `/recommendations` shows:

- a setup message explaining that personalization is optional
- a link to `/?mode=catalog`
- a link to the deployment guide

That unavailable state is expected behavior in backend-free local development and should not compete with the reader-first path.

## Proxy Contract

The web layer uses two backend-backed routes:

- `GET /api/recommendations`
- `POST /api/recommendations`

The browser keeps a stable local `user_id` so recommendations can stay consistent without requiring a full user account system.

## Local Verification

Start the backend:

```bash
uv run uvicorn ai_web_feeds.web_api:app --host 127.0.0.1 --port 8001
```

Point the web app at it:

```bash
BACKEND_URL=http://127.0.0.1:8001
```

Then verify the proxy route:

```bash
curl "http://127.0.0.1:3000/api/recommendations?user_id=test-user&topics=agents,llm&limit=10"
```
