# Search Architecture

Search is now split by responsibility rather than by a hard public/backend
boundary. The key distinction is whether a feature is backed by the
**checked-in catalog files and aggregate post loader** or by **optional runtime
storage services**.

## Public web search

The default web deployment keeps read-only search local-first:

| Surface                      | Backing data                             | Purpose                                                   |
| ---------------------------- | ---------------------------------------- | --------------------------------------------------------- |
| `/api/search?scope=sources`  | checked-in catalog                       | lexical search across source metadata                     |
| `/api/search?scope=articles` | aggregate post loader over matched feeds | lexical search across recent article titles and summaries |
| `/api/search/autocomplete`   | checked-in catalog                       | lightweight prefix suggestions for feeds and topics       |

The public search experience does not require `BACKEND_URL`.

## Optional backend-backed search storage

Two routes still optionally proxy to backend/runtime storage when configured:

- `/api/search` `POST` for search analytics logging
- `/api/search/saved` for saved-search storage

If the backend is not configured, these routes return safe unavailable or
accepted responses instead of breaking the main search UI.

## Web route split

The `/search` page is server-first for any URL that includes `q=...`.
The server shell normalizes the query/filter state, fetches the initial result
set, and hydrates the client with both the result payload and the request
status. Those server-side reads come from local catalog data and recent
aggregate feed scans rather than a remote backend.

### Source search path

Source search ranks lexical matches across:

- source titles
- descriptions
- notes
- source types
- topic labels
- verification state as a tie-breaker

### Article search path

Article search first finds candidate feeds from the catalog, then loads recent
posts for those feeds and ranks the resulting article set lexically with
freshness as a tie-breaker.

### Autocomplete path

Autocomplete stays intentionally lightweight and reads the checked-in catalog
directly. It trims the query, matches by prefix, and returns a small mixed set
of feed and topic suggestions.

<Callout type="info" title="Catalog-first product flow">
  `/feeds` is the primary subset-selection surface. `/search` is the text retrieval layer on top of that catalog. If a user is trying to build an exportable shortlist rather than retrieve text, point them to `/feeds` first.
</Callout>

## Search operations checklist

```bash
uv run ai-web-feeds search query "llm agents" --type full_text --limit 10
uv run ai-web-feeds search query "retrieval augmented generation" --type semantic --limit 10
uv run ai-web-feeds search autocomplete llm --limit 8
uv run ai-web-feeds search embeddings --provider local
```

## Embedding fallback rules

The runtime supports two embedding providers:

- `local`
- `huggingface`

Feed embedding refresh resolves the effective provider in this order:

1. CLI override (`search embeddings --provider ...`)
2. `AIWF_EMBEDDING__PROVIDER`
3. local default

If the effective provider is `huggingface`, the runtime requires
`AIWF_EMBEDDING__HF_API_TOKEN`. Missing tokens, malformed API responses, or API request
failures trigger a fallback to the local Sentence-Transformers path when fallback is
allowed. Saved `feed_embeddings` rows record the provider/model that actually succeeded
so downstream semantic search can regenerate query vectors with matching specs.

## Data dependencies

- public source search reads from `data/feeds.enriched.yaml` or `data/feeds.yaml`
- public article search reads recent entries through the aggregate post loader
- autocomplete reads from the checked-in catalog
- semantic search remains a runtime/CLI concern, not the default public web mode
- saved searches and search logs are optional backend-backed storage concerns, not
  authored YAML
